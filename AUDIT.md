## 2. Аудит кода и архитектуры

### 2.1 Общее качество кода

- TypeScript в `strict: true` ([`tsconfig.json:6`](tsconfig.json:6)), но по кодовой базе **169 явных `: any`** в `src/lib` + `src/components` + `src/pages/api` + `src/app` — строгость подорвана на практике.
- **Тестов нет вообще** — ни одного `*.test.*`/`*.spec.*` файла в `src/`. Для проекта с такой сложной state machine оплаты/пробника (см. ниже) это существенный риск регрессий.
- [`src/pages/api/auth.ts`](src/pages/api/auth.ts) — почти 1100 строк, ~25 режимов (`mode`) в одном handler'е, 23 обращения к Redis на файл. Это центральная state machine пробника/оплаты/факультетов/групп — она работает, судя по глубине edge-case обработки (`healStalePreviewForFinalizedUser`, `clearPreviewFlowIfAdminGrantedAccess` и т.п.), но один файл на 25 веток стал практически нечитаемым для нового человека и любое изменение рискует сломать соседний режим. Кандидат на разбиение по режимам/доменам (preview, catalog-browse, faculty, study-group — уже частично вынесены в `src/lib/preview*.ts`, но orchestration остаётся в одном файле).
- `next.config.js:5` — `outputFileTracing: false` отключён **специально, чтобы обойти баг micromatch** (stack overflow при трассировке `node_modules` на Vercel). Побочный эффект: Next не может обрезать неиспользуемые файлы из serverless-бандла, а `subject-data.ts` резолвит JSON-файлы через динамический `require(...)`, который статически не анализируется — велика вероятность, что **весь `src/data/` (~9-13 МБ) попадает в каждую serverless-функцию**, а не только нужный файл. Это стоит перепроверить размером реального бандла на Vercel — если он растёт, это первое, что нужно чинить.

### 2.2 Supabase / БД / RLS

Раздела не существует в том виде, как описано. Supabase используется только для загрузки файлов через REST (`admin-upload.ts`, `admin-upload-sign.ts`) с `SUPABASE_SERVICE_KEY` на сервере — RLS-политики нерелевантны, потому что нет прямых DB-запросов из клиента. Вся модель пользователей/прогресса/контента живёт в Redis как JSON-блобы под ключами `user_id:{tgId}`. Это значит: нет реляционных индексов, нет транзакций между сущностями, любая аналитика/отчётность потребует либо полного скана всех `user_id:*` ключей, либо отдельного индекса (частично есть — `src/lib/userIndex.ts`, `src/lib/facultyStats.ts`).

### 2.3 Система access-ключей и демо-режима

Подтверждено и работает как описано в контексте:
```ts
// src/pages/api/auth.ts:259-266
const isValidKeyFormat = (key: string): boolean => {
  const k = key.trim();
  if (!/^\d{8}$/.test(k)) return false;
  const d = k.split('').map(Number);
  const sumCheck = d[0] + d[1] + d[7] === 15;
  const modCheck = parseInt(k, 10) % 7 === 3;
  return sumCheck && modCheck;
};
```
Это **не единственная защита** — это быстрый локальный фильтр перед `redis.sismember('valid_keys', key)` ([`auth.ts:1054`](src/pages/api/auth.ts:1054)), то есть ключ должен и пройти математическую проверку, и реально существовать в Redis-множестве, и после активации удаляется (`srem`, [`auth.ts:1079`](src/pages/api/auth.ts:1079)) — одноразовый. Обойти сложно: даже зная формулу, случайный перебор 8-значных чисел, удовлетворяющих условию (примерно 1 из 70 комбинаций), всё равно упрётся в `sismember`-проверку и rate-limit ([`auth.ts:289-314`](src/pages/api/auth.ts:289): 3 попытки → блок на 2 часа, эскалация до 12 часов за повтор). Разумная схема для такого масштаба.

### 2.4 Аутентификация

Две параллельные, не пересекающиеся системы:
1. **Telegram Mini App**: `initData` HMAC-верификация — [`src/lib/verifyInitData.ts`](src/lib/verifyInitData.ts).
2. **Веб-логин** ([`src/lib/webAccount.ts`](src/lib/webAccount.ts), [`src/lib/sessionCookie.ts`](src/lib/sessionCookie.ts)): пароли — `scryptSync` с 16-байтовой солью, сверка через `timingSafeEqual`; сессии — HMAC-SHA256-подписанная cookie `bn_sid`, `HttpOnly; SameSite=Lax`, `Secure` в проде, TTL 30 дней, анти-шаринг через ротацию `sessionId` при повторном логине ([`web-auth.ts:76-78`](src/pages/api/web-auth.ts:76)). **Сделано корректно** — это не JWT, но подход добротный (secret по умолчанию — fallback на `BOT_TOKEN`, если `SESSION_SECRET` не задан ([`sessionCookie.ts:7-9`]) — стоит явно завести отдельный `SESSION_SECRET`, чтобы не связывать два разных секрета).

### 2.5 Безопасность админ-панели — реальная дыра

- `AdminPatternLock.tsx:225` — **захардкожен plaintext-секрет** `ADMIN_UNLOCK_SECRET = 'ortho2000secret'`, который уходит в клиентский JS-бандл и виден любому, кто откроет devtools.
- `Admin.tsx:2005-2006` отправляет этот секрет как поле `secret` в запросах к admin-API.
- Часть admin-роутов проверяет **и** секрет, **и** Telegram `initData` HMAC против `ADMIN_TG_ID` (`admin-users.ts`, `admin-config.ts`, `admin-faculty-stats.ts` — надёжно).
- Но `admin-glossary.ts:35-37`, `admin-whitelist.ts:13-15`, `admin-upload.ts:19`, `admin-upload-sign.ts:13` проверяют **только** секрет — без проверки личности. Поскольку секрет вытащить из бандла — секунды, **любой человек может curl'ом редактировать глоссарий, вайтлист и заливать файлы в Supabase Storage от имени приложения**, без доступа к Telegram-аккаунту админа. Это нужно закрыть в первую очередь — привести все `admin-*` роуты к единому стандарту (секрет + `initData`-проверка), не полагаясь на клиентский pattern-lock как security-барьер (он и не должен им быть, это UX-гейт).

### 2.6 Telegram-бот (webhook)

[`src/app/api/bot/route.ts`](src/app/api/bot/route.ts):
- Весь `POST`-хендлер обёрнут в try/catch, всегда возвращает `200 {ok:true}` даже при ошибке (`:131-134`) — хорошо, не будет retry-шторма от Telegram.
- **Нет проверки `X-Telegram-Bot-Api-Secret-Token`** — ни в хендлере, ни при регистрации вебхука (`scripts/set-webhook.mjs:9-17` не передаёт `secret_token`). Это значит **эндпоинт открыт**: кто угодно, зная URL (он не секретный — это публичный webhook path), может POST'ить поддельные Telegram-апдейты — например, форджить `chat_member: left` событие для произвольного `userId` и выставлять `unsub:{userId}` в Redis ([`route.ts:80-85`](src/app/api/bot/route.ts:80)), либо просто спамить обработчик.
- **Нет идемпотентности** по `update_id` — ретрай от Telegram при сетевом сбое повторно выполнит `/start`/`/admin` логику (для этих конкретных команд цена невысокая, но паттерна на будущее нет).
- Обработка синхронная: `isSubscribed` (до 4с) + `tgSend` (до 8с) выполняются до ответа Telegram — при холодных стартах может подойти к лимиту времени выполнения функции.

### 2.7 AI-пайплайн

Реальная схема — цепочка fallback между тремя провайдерами (Timeweb DeepSeek → Groq Llama → Gemini), без RAG/embeddings, контекст — сырой текст вопроса. Доступ гейтится проверкой оплаченного доступа ([`ai/question/route.ts:20-25`](src/app/api/ai/question/route.ts)), но **нет rate-limit на AI-вызовы** — авторизованный платный пользователь может долбить эндпоинт в цикле и раскручивать счёт за Timeweb/Groq/Gemini API. Также не найдено единого таймаута/`AbortController` на эти fetch-вызовы (в отличие от `telegramApi.ts`, где таймаут явный) — при зависании внешнего провайдера запрос может держать функцию до платформенного лимита.

### 2.8 JSON-контент и рост

Модель "по 3-4 файла на предмет" сама по себе разумнее единого монолита и явно задокументирована как паттерн для добавления новых предметов ([`subjects.ts:1-15`](src/lib/subjects.ts:1)). Проблемы не в структуре, а в загрузке и дублировании:
- `subject-data.ts` грузит файл целиком через `require()`, отдаёт клиенту весь массив без пагинации — при файлах 300-650 КБ это не критично, но с ростом до 20+ предметов совокупный объём и время `JSON.parse` на холодном старте будут расти линейно.
- Экзаменационные билеты (`ticketsData.json` и аналоги) дублируют текст вопрос/ответ инлайн вместо ссылки на ID — при росте это дублирование контента будет расти быстрее, чем нужно.
- Реальный риск для масштабирования — не размер файлов, а `outputFileTracing: false` (см. 2.1): если весь `data/` действительно попадает в каждую функцию, рост числа предметов будет утяжелять **все** функции разом, а не только те, что реально используют новый JSON.

### 2.9 Redis / лимиты бесплатных тиров — что сломается первым

- `auth.ts` — 23 обращения к Redis в отдельных ветках на один запрос, `admin-users.ts` — 19. `check_subjects` (вызывается при каждом открытии приложения) идёт по цепочке `get user → sismember whitelist → isSubscribed (внешний HTTP) → maybeExpirePreviewUser → healAndMaybePersistUser → mergeGroupAccess → buildPreviewSubjectCatalog` — это уже реализовано с деградацией (`redisDegraded.ts` детектит quota-ошибки Upstash по тексту и отдаёт fallback-ответ), **и сам факт наличия этого кода намекает, что лимит Upstash уже реально задевали в проде**.
- Двухбэкендная схема (`redis.ts:34-61`): нативный ioredis (Timeweb) в приоритете, Upstash/Vercel KV как fallback — если прод реально на Timeweb (см. раздел 0), то "лимиты бесплатного тира Upstash/Vercel" могут вообще не быть узким местом — тогда это лимиты Timeweb-тарифа, которые в репозитории не видны и надо уточнять у автора напрямую.
- **Вывод:** прежде чем оптимизировать под "лимиты Vercel/Supabase free tier", нужно зафиксировать, какой хостинг реально в проде — это первый вопрос, а не архитектурная деталь.

## 3. Аудит дизайна и UX

### 3.1 Цветовая система и тема Telegram

`globals.css` — полноценная система CSS custom properties (`--background`, `--c-card`, `--c-text` и т.д.) с тремя темами (light/dark/dark+bright «AMOLED»), корректно прокинутая в `tailwind.config.js`. Это не хаос из хардкода на уровне инфраструктуры. **Но** тема переключается вручную через `localStorage.getItem('theme')` ([`layout.tsx:37-45`](src/app/layout.tsx:37)) с дефолтом `'dark'` — приложение **не читает** `tg.colorScheme`/`tg.themeParams`/`--tg-theme-*` вообще (0 совпадений по всему `src/`). То есть тема визуально не синхронизирована с системной темой Telegram пользователя — если у студента светлый Telegram, а приложение по умолчанию открывается тёмным, это заметный, хоть и не критичный, диссонанс. Быстрый фикс (часы) — прочитать `tg.colorScheme` один раз при первом запуске как дефолт.

При этом отдельные экраны обходят токены инлайн-хардкодом: `AuthScreen.tsx` использует `#0A0E0C`, `rgba(220,38,38,0.15)` и т.п. вперемешку с теми же CSS-переменными в одном файле — несогласованно, но чинится find/replace.

### 3.2 Safe-area — три независимые реализации, одна мёртвая

Быстрый фикс — удалить мёртвый `TelegramProvider.tsx`. Средний по трудозатратам — свести (1) и (2) к одному источнику истины, иначе любое будущее изменение safe-area придётся вносить дважды и они разойдутся.

### 3.3 Онбординг — реально проработан

`AuthScreen → ChannelCodeEntryScreen → PreviewGroupScreen → PreviewOnboardingScreen`: один тап на код факультета, номер группы, затем двухшаговый визард выбора предмета/раздела на `framer-motion`. Есть shake-анимация на ошибку, back-кнопки на большинстве шагов, приветственный оверлей. Это выглядит осознанно спроектированным, а не «на коленке». Единственный конкретный пробел — `PreviewGroupScreen.tsx` не имеет кнопки назад/пропустить (только «Продолжить», строки 92-105) — студент, попавший на этот шаг, не может выйти назад. Фикс на час.

### 3.4 Мобильная эргономика

- Основные CTA стабильно `h-[52px]` во всех ключевых экранах — хорошо, осознанная консистентность.
- `TestsTab.tsx` — несколько иконочных тап-таргетов `w-7 h-7`/`w-8 h-8` (28-32px), ниже рекомендованного минимума ~44px (строки 1313, 1338, 1405) — конкретный, легко фиксируемый баг, но нужно пройтись по всему файлу (1580 строк).
- `TextWithGlossary.tsx` хардкодит `text-white` (строки 51, 74, 79, 98) вне зависимости от активной темы — в светлой теме текст рискует быть нечитаемым (белым по светлому). Плюс тултип термина позиционируется по `e.clientX/clientY` без клэмпинга к границам экрана — может улетать за край у экрана. Это не просто стиль, а реальный баг, фикс на часы.
- `Navigation.tsx` — нижняя pill-панель, удобная одноручная зона, с long-press для смены игрового режима — но эта логика продублирована между `Navigation.tsx` и `QuestionsTab.tsx` вместо общего компонента (а `components/game/`, куда это явно должно было переехать, пусто).

### 3.5 Дизайн-система по факту игнорируется

Из ~37 компонентов верхнего уровня `Button`/`Card` из `ui/` реально используют только 3 (`AuthScreen`, `GroupAccessHintModal`, `AccessWelcomeOverlay`). `QuestionsTab`, `TestsTab`, `TasksTab` — каждая карточка/кнопка это руками собранный `<div>` с инлайн `style={{ background: 'var(--c-card)' }}`. Визуально это не выглядит рассинхронизированным (все используют одни и те же CSS-переменные), но `ui/Card`/`ui/Button` по факту декоративны — любое глобальное изменение (радиус, тень, состояние нажатия) придётся вручную вносить в десятки мест. Это единственный по-настоящему стратегический дизайн-долг здесь — не срочно, но при дальнейшем росте кодовой базы стоит консолидировать в общие примитивы (дни работы).

## 4. Аудит продукта и монетизации

### 4.1 Переход «инструмент для сессии» → «платформа на весь год»

Раздел «Занятия» (`src/lib/curriculum.ts`, `curriculumSeed.ts`, `src/data/programs/*`, `LessonsTab.tsx`, `AdminCurriculumTab.tsx`) реально существует и уже подключён в основной интерфейс: `page.tsx` рендерит `<LessonsTab>` на вкладке `lessons`. Модель данных типизирована (`Program → Lesson/Lecture → LessonSection`) и хранится в Redis, а не в плоском JSON — это архитектурно более здравый паттерн, чем остальной контент, и его стоит использовать как образец при последующем расширении на другие предметы. Но охват сейчас узкий — только анатомия, 2 факультета (стоматология, педиатрия), 1-2 курс, судя по 10 файлам в `data/programs/` и последним коммитам ("update pediatrics anatomy lectures..."). Это реалистичное направление, но сейчас это MVP одного предмета, а не полноценный круглогодичный слой поверх всех 11 дисциплин — до полноценного «репозиционирования вокруг 6-летнего цикла» нужно последовательно закрыть остальные предметы тем же паттерном.

### 4.2 SM-2 / streaks / лидерборды — с нуля

Ничего из этого не реализовано. `studyEngine.ts` — статический взвешенный выбор по метаданным контента (`exam_weight`, `difficulty` и т.д.), не персонализированная адаптация под конкретного студента (нет хранения истории ответов/ease factor на пользователя). Это значит внедрение SM-2 — не «докрутить существующее», а построить новый слой: (а) где-то нужно писать per-user per-question историю ответов (сейчас в Redis-блобе пользователя такой структуры нет), (б) нужен job/триггер для push-уведомлений о повторении. Инфраструктура для уведомлений частично есть (`send-start-message.ts`, `send-fullscreen-button.ts`, `notifyAdmin.ts` — но это ручные/событийные, не cron/scheduled), так что технически канал доставки напоминаний уже есть, просто ничего не расписывает по расписанию. Чтобы не выглядеть «приклеенной геймификацией» — не делать отдельный «SM-2 экран», а встраивать напоминания в уже существующий, хорошо продуманный онбординг/навигационный слой (см. раздел 3.3-3.4) как естественное продолжение, а не новую фичу поверх.

### 4.3 Подписочная модель и удержание после сессии

Ценообразование модульное и гибкое ([`previewPricing.ts`](src/lib/previewPricing.ts)) — по предмету/модулю, с точечными акциями (`PHARMA_EXAM_DATE`-привязанная скидка "осталось N дней до экзамена" — это уже пример неплохого, contextual retention-триггера). Но вся модель оплаты завязана на ручное подтверждение админом (СБП-перевод → «скинул чек» → админ подтверждает вручную, поллинг каждые 45с) — рабочий процесс для текущего масштаба, но это явное узкое место при росте: чем больше платящих студентов, тем больше ручной нагрузки на одного человека (владельца), и тем длиннее задержка между оплатой и доступом — что бьёт по конверсии именно в пиковые дни перед экзаменом, когда объём заявок скачком растёт. Второй риск для удержания — сама структура: система заточена под «купил доступ к разделу → прошёл экзамен → всё» без встроенного крючка на возврат после сессии (раздел «Занятия» такой крючок как раз создаёт, но пока узкий).

### 4.4 DENCLAS

Не найдено в коде вообще — либо это отдельный, не связанный с этим репозиторием научный проект (документ+презентация для СНО, судя по описанию, может существовать вне кода), либо ещё не начато интегрироваться. Без доступа к самому материалу DENCLAS нельзя дать предметную рекомендацию по встраиванию — тут нужно решение автора о формате: как отдельный «научный» раздел в приложении (репутационная фича, витрина для абитуриентов/олимпиад) или как часть контента по стоматологии. Рекомендую отдельно уточнить, где сейчас живёт DENCLAS-контент, прежде чем планировать интеграцию.

### 4.5 Расширение на новые предметы

Судя по `data/`, экспансия уже идёт быстрее, чем можно было предположить по описанию — помимо ортопедии и микробиологии есть биология (+3 факультетских варианта), анатомия, гистология, биохимия/физиология (`fizo`), фармакология, химия, терапия, английский — то есть 10-11 предметов, а не 2. Паттерн добавления нового предмета уже задокументирован и относительно механический (`subjects.ts:1-15`). Учитывая находки раздела 2.5 (дублирующиеся `bio_questions*.json`) — прежде чем добавлять предметы дальше, стоит навести порядок в уже существующих факультетских вариантах, иначе задвоение будет расти пропорционально числу предметов.

### Стратегические изменения (месяц+)

1. **SM-2 spaced repetition с per-user историей** — потребует нового слоя данных (история ответов на вопрос/пользователя, не просто веса в контенте), плюс scheduled-механизм для расчёта следующего повторения и триггера push через уже существующие `send-*` эндпоинты. Делать это сейчас имеет смысл именно потому, что раздел «Занятия» уже создаёт годовой ритм использования — SM-2 логично встраивается в него как второй крючок, а не отдельная фича.
2. **Автоматизация подтверждения оплаты** — текущая ручная схема (чек → ожидание админа → подтверждение) не масштабируется на рост платящих студентов; стоит оценить автоматическую сверку по СБП API/банковской выписке, если объём вырастет настолько, что ручное подтверждение станет узким местом (сигнал к действию — не сейчас, а когда очередь подтверждений начнёт заметно расти в пиковые дни).
3. **Консолидация дизайн-системы** — свести повторяющиеся inline-карточки/кнопки в `ui/Card`/`ui/Button` с реальным использованием по всей базе. Не срочно (визуально сейчас консистентно за счёт CSS-переменных), но при дальнейшем росте числа экранов это станет дорого чинить точечно.
4. **Пересмотр модели контента при росте числа предметов** — если экспансия продолжится в темпе, видимом сейчас (уже 10-11 предметов вместо изначальных 2), стоит спланировать переход от плоских JSON-файлов к нормальной схеме (даже без полного перехода на SQL — например, единый Redis/KV индекс с ID-ссылками вместо копирования текста) до того, как дублирование (как с `bio_questions.json`) станет массовой проблемой, а не единичным случаем.
